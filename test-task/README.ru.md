# Тестовое задание: BrownEvents

> Read in English: [README.md](README.md)
>
> Русская версия предназначена для удобства чтения. Файлы задач и сайд-квестов остаются на английском, который используется как рабочий язык проекта. Issues в вашем репозитории тоже должны быть на английском.

BrownEvents представляет собой приложение для управления конференциями, которое не поддерживалось два года. Оно уже умеет создавать конференции, показывать сессии и регистрировать участников.

Ваша задача состоит в том, чтобы разобраться в существующей системе, стабилизировать её и реализовать две новые функции с помощью консольного AI-агента. Проверяется как результат, так и процесс работы, поэтому у задания есть правила трассировки, журнал разработки и финальный аналитический отчёт.

## Ожидаемый срок

Ориентируйтесь примерно на от 14 до 20 дней с момента получения доступа к репозиторию.

Это не жёсткий дедлайн. Если понадобится больше времени, сообщите проверяющему.

## Проект

Стек:

- ASP.NET Core 6
- EF Core 6
- React
- Vite
- PostgreSQL

Перед началом задач запустите приложение:

```bash
docker-compose up
```

Убедитесь, что окружение работает.

## Правила трассировки

Каждая задача должна прослеживаться по следующей цепочке:

```text
GitHub Issue
→ ветка
→ сессия агента
→ коммиты
→ Pull Request
```

Для каждой задачи соблюдайте следующие правила.

1. Создавайте отдельную ветку. Используйте ID задачи и короткий slug.

   ```bash
   git checkout -b BEVN-001-codebase-map
   ```

   Запускайте агента для этой задачи только из этой ветки.

2. Начинайте первое сообщение каждой сессии агента с ID задачи.

   ```text
   BEVN-104: приведи ответы API к единому формату...
   ```

   Аналитический отчёт использует первое сообщение для идентификации сессии.

3. Добавляйте ID задачи в связанные коммиты.

   ```text
   docs: add architecture map (BEVN-001)
   ```

4. Создавайте отдельный Pull Request для каждой задачи из её ветки в `main`.

   Pull Request должен:
   - содержать ID задачи в заголовке;
   - ссылаться на соответствующий GitHub Issue через `Closes #N`;
   - выполнять Definition of Done задачи;
   - включать обязательное обновление devlog.

   Проверьте результат, затем смержите Pull Request самостоятельно и переходите к следующей задаче.

Количество сессий агента, попыток и уточнений не ограничивается и само по себе не оценивается. Проверяющий смотрит на то, как вы ставите задачи, проверяете решения, исправляете проблемы и доводите работу до результата.

## Процесс разработки

Для задач используются два режима.

### Свободный режим

Предписанного процесса работы с агентом нет. Используйте подход, который позволяет выполнить и проверить задачу.

### Spec-driven

До начала реализации подготовьте:

1. спецификацию, которая описывает ожидаемый результат и разрешает спорные или неясные случаи;
2. план реализации с шагами разработки и проверки.

Оба документа должны быть закоммичены в ветку задачи вместе с реализацией.

Если вы используете Claude Code, установите плагин [superpowers](https://github.com/obra/superpowers) и используйте его процесс brainstorming, specification, planning и implementation. Документы сохраняются в `docs/superpowers/`.

Если вы используете другого консольного агента, воспроизведите эквивалентный процесс. Pull Request должен содержать `spec.md` и `plan.md`.

Spec-driven режим используется для:

- EXT-150 на треке B;
- BEVN-202;
- BEVN-203;
- BEVN-205.

### CI gate

EXT-110 восстанавливает CI.

Начиная со следующей задачи, мержите Pull Request только при зелёном CI. Если пайплайн сломался из-за ваших изменений, его исправление входит в текущую задачу.

## Журнал разработки

Ведите `docs/devlog.md`.

Добавляйте короткую запись после каждой задачи. Она должна отражать ваши выводы о проделанной работе, а не пересказывать diff.

Записывайте то, что важно:

- что вы изменили и какой результат получили;
- какие решения агент принял самостоятельно и приняли ли вы их;
- где пришлось вмешаться вручную;
- что вы сделали бы иначе в следующий раз.

Запись можете написать вы или агент, но она должна отражать вашу оценку работы.

Шаблон Pull Request содержит чекбокс `devlog updated`. Задача не считается завершённой без записи в devlog.

Devlog также понадобится на финальной защите, поэтому обновляйте его сразу после задачи.

## Финальный отчёт

После мержа всех обязательных задач выбранного трека создайте аналитический отчёт из каталога репозитория:

```bash
npx -y -p @codemieai/code codemie analytics --report \
  --last 30d --include-external \
  --project brown-events-pilot \
  --report-format both --report-output ./report/report.html
```

Аргумент `--project brown-events-pilot` фильтрует сессии по имени каталога репозитория. Если ваша локальная папка называется иначе, используйте её имя.

Окно `--last 30d` покрывает ожидаемые от 14 до 20 дней работы. Если работа заняла больше 30 дней, укажите точные даты через `--from` и `--to`.

Перед отправкой:

1. Откройте `report/report.html` в браузере.
2. Убедитесь, что отчёт содержит только сессии этого проекта.
3. При необходимости проверьте [codemie-analytics.md](codemie-analytics.md), чтобы уточнить содержимое отчёта. В него входят метрики сессий, ветки и первое сообщение каждой сессии. Полные диалоги и содержимое файлов не включаются.
4. Закоммитьте оба файла:
   - `report/report.html`
   - `report/report.json`

5. Создайте и смержите финальный Pull Request.
6. Сообщите проверяющему, что задание завершено.

## Оценка

Проверяющий оценивает:

- выполнение Definition of Done каждой задачи;
- качество кода и документации;
- спецификацию и план для spec-driven задач;
- соответствие реализации этим документам;
- трассировку от задачи к сессиям агента, коммитам и Pull Request;
- зелёный CI для мержей после EXT-110;
- то, как вы используете агента, проверяете его работу и разбираете принятые им решения;
- объяснение своей работы на финальной защите.

Количество попыток и сессий агента само по себе не является критерием оценки.

## Вопросы

Если приложение не запускается, сборка падает по причинам, не связанным с вашей работой, или формулировка задачи непонятна, обратитесь к проверяющему вместо того, чтобы тратить дни на догадки.
