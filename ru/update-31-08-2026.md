# Обновление по позициям

В конце рабочей недели наконец-то смог поговорить с несколькими Delivery Managers проектов (плюс мне дали контакты ещё нескольких — узнать, смогут ли они открыть позиции).

Почти все проекты — это легаси-проекты с историей разработки и поддержки от 10 лет. Там, естественно, горы кода и зоопарк систем. Поэтому разработка — это про правильно понять требования, уточнить, реально ли это надо делать и как (бывает, что делать лучше не надо), и дальше решить, как это можно сделать, ничего не сломав. Нового кода разработчики пишут мало — скорее разбирают и читают имеющийся.

Все работают с AI. Бюджет на AI Usage — 150–300$ в месяц на разработчика. Поэтому надо быть бережливым: разбираться в [основах токеномики](../en/requirements/ai-sdlc.md) и не запускать тяжёлые пайплайны там, где можно быстро поправить код руками.

Позиции называются «AI Native», но название отчасти обманчиво: да, код пишет AI, однако это малая часть работы. Основное — разбираться в текущей кодовой базе, ревью, согласования и тщательная проверка. Классические инженерные знания и практики разработки — это по-прежнему 70–80% того, чем должен владеть AI Native инженер; AI меняет не состав этих знаний, а способ их применения.

У найма два интересанта. EPAM нанимает вас к себе, а не к клиенту: клиент может смениться, проект — закрыться, и департаменту важно, что вы знаете AI-процесс и терминологию, — такому человеку проще найти следующий проект. Проекту важен стек: «нам вайбкодеры не нужны» — берут на Java, будут собеседовать по Java; берут на фронтенд — по фронтенду.

Общие требования для всех позиций:

- English — B1+. Обычно много коммуникации: уточнение требований, edge cases, обсуждение с feature owner, etc.
- Понимание SDLC — что именно нужно знать и уметь, см. [Требования по SDLC](../en/requirements/sdlc.md)
- Fast learner, желание разбираться в новом, критическое мышление — это то, что я слышу от проектов, когда они описывают кандидата.

Из вопросов, которые звучали на собеседованиях (по части [AI SDLC](../en/requirements/ai-sdlc.md)):

- Как бы вы онбордили агента в проект?
- Зачем придумали хуки?
- Какой контекст получает агент при старте сессии?

## Позиции

### 1. Angular-разработчики в Польше (Краков, Вроцлав, Гданьск)

Большая платформа в области supply chains / logistics. Много команд и направлений.

Требования:
- Уверенные знания Angular, TypeScript
- Понимание [SDLC](../en/requirements/sdlc.md). Понимание и опыт с [AI SDLC](../en/requirements/ai-sdlc.md) для этого проекта не важны — всему учат по ходу
- Проживание в Польше (Краков, Вроцлав, Гданьск), наличие на руках действующей карты побыта

Про Польшу отдельно: статуса student там нет — по закону найм сразу означает трудовой договор с обязательствами, поэтому проект открывает позицию, только когда она точно нужна (например, контракт с заказчиком требует, чтобы разработка была в ЕС). Тестовое задание всё равно стоит сделать: когда позиция откроется, кандидата с готовым результатом проще предложить.

### 2. Проект в области разработки систем поиска и агрегации больших данных (Java, React, NodeJS)

Открытые Junior-позиции:

1. React / Next.js + понимание Node.js; Core JS / TS / Unit Tests / Playwright
2. React / Next.js + понимание Node.js; Core JS / TS / Unit Tests / Playwright + знание стандартов accessibility
3. React / Next.js + понимание Node.js; Core JS / TS / Unit Tests / Playwright + знание стандартов accessibility
4. Java + понимание React/Node.js на уровне чтения кода
5. Java / Spring / Microservices (плюс в идеале понимание Node.js)

Требования:
- Страны: Грузия, Узбекистан, Казахстан, Кыргызстан, Армения
- Знание тестовой пирамиды обязательно (E2E/Unit/etc.) — на проекте нет тестировщиков, всё тестирование осуществляется автотестами. Используют Cypress и Playwright.
- Обязательно знание русского языка
- Для Java-позиций (4 и 5): знание Java Spring Boot; желательно понимать, что такое AWS
- Понимание [SDLC](../en/requirements/sdlc.md) и [AI SDLC](../en/requirements/ai-sdlc.md)

Условия:
- Первые 3 месяца (уже после прохождения всех интервью) — позиция «On Training», 500$. По факту это аналог испытательного срока.
- Следующие 6+ месяцев — 800–900$ (позиция всё ещё non-billable; райз возможен только после перехода на billable. Гарантий, что billable будет, никто дать не может.)

Как выглядит работа — со слов разработчика с этого проекта (Q&A 1 сентября):

- Фабрике отдаётся практически номер тикета: она читает story и контекст, задаёт уточняющие вопросы и выдаёт черновой PR. Ценность разработчика — проверить этот PR: не ломает ли существующее, не переписал ли агент тесты «под себя», где слабые места (например, optional chaining на данных с бэка — без него может лечь прод), не задевает ли изменение другие репозитории.
- Надёжность: весь новый код под feature flags с постепенным раскатыванием. Каждый PR идёт с юнит-тестами: гейт Sonar — 80%, ревьюеры просят ~100% на новый код, существующий покрыт на ~95%. Юнит-тесты пишет агент — задача разработчика проверить, что они проверяют реальные сценарии, а не просто дают покрытие. E2E и синтетики — отдельные stories; Cypress выпиливают в пользу Playwright.
- Тестировщиков нет: accessibility проверяют сами разработчики (клавиатура, скринридеры NVDA / VoiceOver), manual testing по таблице acceptance criteria — отдельная story, потом демо feature owner'ам.
- Стек: React 18, Next 14, TypeScript 5; микросервисы и микрофронты (все на React/Next); встречаются репозитории на JS без TypeScript. Репозитории, которыми владеют много команд, «не владеет никто» — там дубли и по три одинаковых хелпера.
- PR-описания от агентов огромные, их никто не читает; ревьюеры всё больше доверяют агентам-ревьюерам. Значит, ответственность на том, кто открыл PR: на ревью должен приходить максимально готовый PR.
- Пример: одну и ту же правку нужно было внести в четыре репозитория. Первую разработчик сделал руками (формирование ссылки — надёжнее написать самому, чем проверять агента), вторую — фабрикой по референсу. Логику агент сделал правильно, но типы приходят из пакета бэкенда, и вместо того чтобы обновить типы в репозитории бэкенда и поднять версию пакета, он расставил `as any`. Технически работает, на ревью не пройдёт. На собеседовании спросят ровно это: откуда берутся типы и почему так нельзя.
- Собеседование: примерно 60% — база (JS/TS, React, браузер, как фронт общается с бэком), остальное — понимание AI-процесса и терминов.

## Про тестовое задание

- Дедлайна нет, но откладывать не стоит: это не курс, а способ показать, что вы работаете с агентом. Сделанное задание — это пометка «знает AI», с которой я иду к проектам.
- Что считается достаточным: разобрались с картой кодовой базы, сделали миграцию или end-to-end story по spec-driven процессу — можно идти на проект. Дальше проект собеседует по стеку сам (см. выше).
- Аналитику запускайте не в конце, а после первой же таски — увидите, сколько она стоила.
